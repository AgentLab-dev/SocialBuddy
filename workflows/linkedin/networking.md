# Workflow: networking

## Purpose

Prepare **human** networking: who to learn from, what to say in a comment, when a connection request is even appropriate. SocialBuddy drafts; the operator sends.

## Inputs

- Operator intent (learn, hire, sell, peer group).
- Audience hypotheses.
- Public excerpts the operator already has permission to see (posts they opened in the UI).

## Procedure

1. **Classify** each target action: `lurk_and_learn`, `public_comment`, `connect`, `message`.
2. **Comments first.** Use `phd-reading` on the target post; draft a comment that adds evidence or a precise disagreement (`phd-writing`). Empty compliments fail the rubric.
3. **Connection requests:** only if a *specific* shared context exists (event, thread, mutual work). Draft ≤300 characters, no pitch deck, no fake “loved your post” if you did not read it.
4. **Messages / InMail:** same as approval-gate writes. One purpose. No sequences in this workflow.
5. Produce an **approval packet** per outbound item (see approval-gate). Batch packets still require per-payload hashes.

## Hard stops

- No auto-invite, auto-follow-up, or visit-bombing.
- No scraped emails to “find them on LinkedIn.”
- No pretending you met someone you did not.

## Example

> **Example** — illustration only.

Draft comment: “Your merge incremental note skips late-arriving keys — we page on uniqueness rather than runtime. What lookback do you use?” Not sent until approved.
